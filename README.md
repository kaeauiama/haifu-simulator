# 配賦・決済シミュレータ（S/4HANA Cloud Public Edition もどき）

設計ワークショップで、配賦・決済の組み方を描き、金額を流して、パターン同士を比べるブラウザツール。SAP には接続しない単独ツールで、結果は SAP の考え方に沿った「もどき」の仕訳で示す。データはブラウザの外に送らない。

- 仕様：[docs/requirements.md](docs/requirements.md)
- 決定・暫定解釈・未決事項：[docs/decisions.md](docs/decisions.md)

## 前提と注意

- SAP には接続しない単独ツール。設定の自動生成や転送もしない
- 仕訳と勘定科目は SAP の考え方に沿った「もどき」。勘定科目は YCOA に番号の体系を寄せた架空のもので、実在の科目番号とは一致しない。結果も実機の結果と一致するとは限らない
- データはブラウザの中（IndexedDB）とファイルだけに置き、外には送らない
- 金額は円の整数で、借方を＋、貸方を−で持つ（売上はマイナス）
- 利益センタ間の配布・配賦では、送信利益センタに導出される全対象の残高を配り、利益センタに計上する（原価センタの残高は動かない）
- 来歴の「遡れない額」は、残高0の原価センタを貸方にした間接費計算・活動配分など、一次仕訳に結びつかない額
- MVP で扱わないもの：指図（WBS で代用）、手動の振替、計画データ。WBS を配賦の送信側にする組み方は、テナントで確認するまで実行しない
- 一次仕訳の CSV は、列「仕訳ID, 勘定, 対象種類, 対象ID, 金額, テキスト」。対象種類は CCTR / WBS / PSEG / PCTR。収益性セグメントの対象ID は特性値を `|` でつないだもの（未設定は `*`）

## サンプル

入出力画面（またはCLI の `--sample railway`）から生成できる。

- **サンプル商事**（要件書 8.1）：5.1 の各ステップを一通り動かすための小さな会社。テストの基準
- **みどり川電鉄**（要件書 8.1.1）：架空の私鉄。最終的に駅ごとの収益性を見る。本線24km・8駅とみどり台線6km・3駅、1か月の営業収益 約5.6億円、営業利益 約8千万円（約14%）

みどり川電鉄の値はすべて架空。ただし、次の傾向に合わせた。

| 項目 | 置いた値 | 参考にした傾向 |
| --- | --- | --- |
| 営業費の区分 | 線路保存費＝工務部、電路保存費（架空電車線・変電所・信号）＝電気部、車両保存費＝車両部、運転費＝運転区、輸送管理費＝運輸指令所、運輸費（駅務）＝駅管区 | 鉄道事業会計規則の営業費の区分と、各区分に入る作業・人件費の範囲（[福岡市地下鉄の損益計算書](https://subway.city.fukuoka.lg.jp/subway/management/pdf/settlement/h30/profit_and_loss.pdf)、[横浜市交通局の事業計画](https://www.city.yokohama.lg.jp/city-info/yokohamashi/org/kotsu/jigyoukeikaku/r3jigyoukeikaku.html)） |
| 費目 | 人件費、動力費、修繕費、業務委託費、租税公課、減価償却費など | 鉄道会社の営業費の費目の分け方（[JR東海 ファクトシート](https://company.jr-central.co.jp/ir/factsheets/_pdf/factsheets2023-08.pdf)） |
| 動力費 | 車両キロ 約94万／月 × 約1.93kWh × 19円 ≒ 3,440万円 | 関東大手私鉄で電車1両を1km走らせる電力量は約2kWh、2016年度の単価は約14円/kWh（[乗りものニュース](https://trafficnews.jp/post/86352)）。単価はその後の値上がりを見込んで19円と仮定 |
| 定期の割合 | 運賃収入の約36% | 私鉄・地下鉄で定期は旅客運賃の約34〜38%、運輸雑収は営業収入の約4〜9%（[九州運輸局の資料](https://wwwtb.mlit.go.jp/kyushu/content/000345204.pdf)） |
| 駅業務 | 中央・川辺・港などは直営、工業団地駅とみどり台線の3駅は委託 | 乗車人員の多い駅や終端の駅は直営、それ以外を委託する方針の例（[仙台市交通局](https://www.kotsu.city.sendai.jp/kigyou/keiei/keiei_minaoshi/pdf/r051114_2_itaku.pdf)） |
| 駅への配り方 | 線路・電路は駅勢キロ、運転費・輸送管理費は列車キロ、車両保存費・動力費は車両キロ、駅務は駅務量 | 線区別収支の試算でよく使われる「量で変わる費用は輸送量の比、路線があるだけでかかる費用は距離の比」という考え方 |

- 人件費は1人あたり月48〜62万円（賞与の引当を含む）と法定福利費15%。社員は約240人で、営業費の約3割
- 減価償却費は営業費の約26%で、設備を持つ部門（電気部・工務部・車両部・駅管区・情報システム部）に置いた
- 運賃は駅で売った分を駅に、Web・定期券センターで売った定期と車内広告は線区全体に計上し、TDD で駅へ細分化する。発着の按分はしていない（発売駅に計上）ので、ターミナルの中央駅の収入が大きく出る
- S/4HANA では、駅のような軸は市場セグメントの拡張項目で足すことが多い。このツールでは特性「地域」に駅コードを入れ、セグメントの表示名に駅名を付けて代える

## 準備

Node.js 22 以上と pnpm 10 を使う。pnpm が入っていなければ、どちらかで入れる。

```bash
corepack enable
```

```bash
npm install -g pnpm@10
```

そのあと依存を入れる。

```bash
pnpm install
```

## コマンド

| コマンド | 内容 |
| --- | --- |
| `pnpm test` | 全パッケージのテスト（engine は 8.2 の T-01〜T-13 を含む） |
| `pnpm typecheck` | 型チェック |
| `pnpm sim` | CLI。サンプル商事の全シナリオを実行して要約を出す |
| `pnpm sim -- --sample railway --compare S-DEFAULT S-PAX` | みどり川電鉄で、駅への配り方を変えた2案の差を出す |
| `pnpm sim -- --scenario S-LATE --journal` | 1シナリオの流れ（送信→受信）を出す |
| `pnpm sim -- --compare S-DEFAULT S-LATE` | 2案の差（利益センタ別・セグメント別・勘定別・対象別、結果が変わったステップ） |
| `pnpm sim -- --trace "CCTR:2000"` | 最終残高の来歴（どの一次仕訳から来たか） |
| `pnpm sim -- --file project.json` | プロジェクト JSON を読んで実行する |
| `pnpm dev` | 画面（開発サーバ。http://localhost:5173） |
| `pnpm build` | 画面の本番ビルド（`apps/web/dist`。CSP 付きの静的ファイル） |
| `pnpm e2e` | 主要な流れの E2E（本番ビルドを CSP 付きで配信し、手元の Microsoft Edge で動かす） |
| `pnpm bench` | 大きい規模（オブジェクト約500件・一次仕訳1万行・ステップ15件）の計測 |

## 性能（3.10 の確認）

`pnpm bench` と画面での計測（2026-10-14、開発用 PC）。オブジェクト514件・一次仕訳1万行・ステップ15件・生成される仕訳約14万行のデータで：

| 項目 | 結果 |
| --- | --- |
| 再計算（Web Worker の中） | 約0.17〜0.2秒（目標1秒以内） |
| 画面向けの値（残高・フロー図・ビュー）を足した時間 | 約0.3秒 |
| 時点を1つ進める・戻す（描き直しまで） | 約0.7〜0.9秒 |
| 編集してから画面に出るまで（300ミリ秒の待ちを含む） | 約1.3〜1.5秒 |
| 金額の構成（直前の送り手／発生元） | 約0.03秒／初回約0.7秒 |

- 図に描く線は、額の大きい順に上限まで（全体のフロー図1,500本、手法別ビュー1,500本、サンキー図400本）。上限を超えたときは「表示 n／m本」と出す
- 自動配置は、ノード300・線600を超える図では使わず、役割ごとの列に並べる（514ノード・1,500本の自動配置に約9秒かかったため）

## 構成

```text
packages/engine   計算エンジン（純粋な TypeScript、UI 非依存）。型・Zodスキーマ、台帳、各手法、検証、来歴、比較、シード、CLI
apps/web          画面（React + Vite + Tailwind + shadcn/ui）。エンジンは Web Worker で動かし、画面は金額を計算せず結果を表示する
docs              要件書と Decision Log
```
